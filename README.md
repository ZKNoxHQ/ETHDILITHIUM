# ETHDILITHIUM

ETHDILITHIUM gathers experiments around DILITHIUM adaptations for the ETHEREUM ecosystem. DILITHIUM signature scheme is a post-quantum digital signature algorithm.


## SPECIFICATION
The repo implements two version of DILITHIUM: one follows the NIST released implementation, and another is tunned for Ethereum Virtual Machine constraints.

Three NIST parameter sets are provided: ML-DSA-44 (`src/ZKNOX_dilithium.sol`, security category 2), ML-DSA-65 (`src/ZKNOX_dilithium65.sol`, category 3) and ML-DSA-87 (`src/ZKNOX_dilithium87.sol`, category 5), see [ML-DSA-65](#ml-dsa-65) and [ML-DSA-87](#ml-dsa-87) below.

## INSTALLATION
**This is an experimental work, not audited: DO NOT USE IN PRODUCTION, LOSS OF FUND WILL OCCUR**

The repo contains a solidity verifier and a python signer.

* **Installation:**
    ```bash
    make install
    ```
    (or `make install_signer` or `make install_verifier`)
* **Generation of test vectors:**
    ```bash
    make gen_test_vectors
    ```
    Generate the test vectors of `test/ZKNOX_dilithium.t.sol` and `test/ZKNOX_ethdilithium.t.sol`.
* **Tests:**
    ```bash
    make test
    ```
     (or `make test_signer` or `make test_verifier`)

Exact figures (`make bench`, solc 0.8.30 via-IR, `optimizer_runs = 1000000`,
see DECISIONS.md ADR-004): 1,006,093, 679,733, 1,198,467 and 1,633,524. The
three NIST figures are execution only: the expanded key travels in the calldata
of every verification with the signature and is read in place from there,
21,216 bytes for ML-DSA-44 (309,468 of calldata per transaction with the
signature, ADR-010), 38,112 bytes for ML-DSA-65 (538,132, ADR-007/008) and
67,680 bytes for ML-DSA-87 (934,400, ADR-012). ETHDilithium keeps its key in an
SSTORE2 blob.

|NTT kernel (256 coefficients) | Gas cost|
|-|-|
|nttFw / nttInv, one coefficient per word, mulmod|181,666 / 215,127|
|nttFwMont / nttInvMont, packed 4x64-bit lanes, radix-8 fused passes, Montgomery|48,152 / 50,881|

Both verifiers run on the packed 4x64-bit-lane layout end to end: z decoded
packed from the calldata with its norm check, the key used in place from the
calldata (ML-DSA-44 and -65) or from its SSTORE2 blob (ETHDilithium),
A.z - c.t1 with two products per multiply on lane-split operands and the
first pass of the inverse NTT folded into it (DECISIONS.md ADR-008, ADR-011),
both NTT directions, hints and w1 encoding
(`src/ZKNOX_NTT_dilithium_mont.sol`, generated by
`pythonref/ntt_mont/gen_ntt_mont.py`, and `src/ZKNOX_dilithium_core_packed.sol`,
checked against the scalar code in `test/`). The NIST verifier runs SHAKE256 on
an external Keccak-f[1600] helper contract bound by code hash
(`src/ZKNOX_shake_fast.sol`, sponge glue and helper bytecode from
fireblocks-labs/evm-ml-dsa-verifier, MIT): deploy it once per chain with
`script/DeployF1600Helper.s.sol` (~4.32M gas) and pass its address to the
verifier's constructor. See `VERSION.md` and `DECISIONS.md`.

Dilithium is an implementation of the NIST standardized signature scheme, where the public key is expanded in order to save computations.
ETHDilithium is an alternative version with a cheaper hash function. Precomputations in the public key has been done in order to accelerate the verification. 

## ML-DSA-44 KEY
`ZKNOX_dilithium` holds no state. The expanded key (A_hat = ExpandA(rho),
t1 = NTT(t1 * 2^13), tr), 21,216 bytes, is passed in the calldata of every
verification: 20 polynomials of `[32][32 words]` (A row by row, then t1), then
tr, the same flat layout as the ML-DSA-65 key (DECISIONS.md ADR-010). `setKey`
checks the length and returns the key, which the caller binds to an account
with keccak256. `encodePubKeyFlat(aHat, tr, t1)` builds it in Solidity
(`script/Deploy_MLDSA_PK.s.sol` `flatKey()`), and from a seed
`pythonref/prepare_pk_for_deployment.py NIST <seed> flat` (the `abi` mode keeps
the SSTORE2 blob of ETHDilithium). Runtime size 22,787 bytes. 

## ML-DSA-65
`src/ZKNOX_dilithium65.sol` verifies ML-DSA-65 (FIPS 204, k = 6, l = 5, tau = 49,
gamma1 = 2^19, gamma2 = (q-1)/32, omega = 55, 3309-byte signatures) with the
same machinery as the ML-DSA-44 verifier: the same NTT kernels and packed
4x64-bit-lane layout, the same SHAKE256 helper binding. What is specific to
the parameter set is in
`src/ZKNOX_dilithium65_core_packed.sol` (20-bit z decode, five-column matvec,
61-byte hints, 4-bit w1 with the gamma2 = (q-1)/32 Decompose) and
`src/ZKNOX_shake_fast.sol` (`sampleInBallFastTau`); the scalar references the
kernels are tested against are in `src/ZKNOX_dilithium65_core.sol`.

* **Key**: the expanded key (A_hat = ExpandA(rho), t1 = NTT(t1 * 2^13), tr),
  38,112 bytes, is passed in the calldata of every verification: 36
  polynomials of `[32][32 words]` (A row by row, then t1), then tr. Nothing is
  stored on chain; `setKey` checks the length and returns the key, which the
  caller binds to an account with keccak256 (DECISIONS.md ADR-007).
  `js/mldsa65.js` `publicKeyToBlob65` produces it from a 1952-byte FIPS 204
  public key.
* **Signer**: JavaScript, `js/mldsa65.js` / `node js/sign65.js` on
  `@noble/post-quantum` (see [js/README.md](js/README.md)); the NIST vectors
  of `test/KAT/` are replayed by `make test_signer65`.
* **Hardware signer**: the ECML-Signer Ledger app
  ([ZKNoxHQ/ecml-signer](https://github.com/ZKNoxHQ/ecml-signer), P2 = `0x01`)
  signs a 32-byte hash in pure mode with an empty context, which is what
  `verify(pk, bytes32 hash, sig)` checks; its public key goes through
  `publicKeyToBlob65` like any other. `test/ecml_signer_compat.t.sol` verifies
  signatures of its v2.4.0 release binary (`HYBRID_SIGN_HASH`,
  `SIGN_TX_MLDSA`): `forge test --match-contract EcmlSignerCompatTest`.
* **KATs** (`test/KAT/`, as given by NIST): `PQCsignKAT_Dilithium3.rsp`
  (100 vectors of the reference implementation's `PQCgenKAT_sign`, pq-crystals/dilithium
  d35ba3f, FIPS 204 ML-DSA-65; count 0 is `test/dilithium65KATS.t.sol`, the
  first 10 counts go through `test/dilithium65_vectors.t.sol`) and the ACVP
  `ML-DSA-65` groups of `ML-DSA-{keyGen,sigGen,sigVer}-FIPS204/internalProjection.json`
  (usnistgov/ACVP-Server 975de31); the 15 sigVer vectors of the external /
  pure interface (contexts of 0..255 bytes, corrupted z, hints, commitment,
  modified messages) are checked on-chain with NIST's expected verdicts.
* **Tests**: `make test_verifier65` (kernel differential and fuzz tests, KAT,
  NIST vectors), `make bench` includes `MLDSA65`.
* **Deployment**: `script/deploy_dilithium65.sh` / `DeployDilithium65.s.sol`
  (needs `F1600_HELPER`, the same Keccak-f[1600] helper as ML-DSA-44; checks
  the NIST KAT on the deployed verifier). One contract per chain, nothing to
  install per key. Runtime size 23,642 bytes.

## ML-DSA-87
`src/ZKNOX_dilithium87.sol` verifies ML-DSA-87 (FIPS 204, k = 8, l = 7,
tau = 60, beta = 120, omega = 75, 4627-byte signatures) in the form of the
ML-DSA-65 verifier. ML-DSA-87 has the gamma1 = 2^19 and gamma2 = (q-1)/32 of
ML-DSA-65, so the z decoder, UseHint and the 4-bit w1 encoding are those of
`src/ZKNOX_dilithium65_core_packed.sol`; what is specific is in
`src/ZKNOX_dilithium87_core_packed.sol` (seven z polynomials with the
beta = 120 bound, seven-column matvec, 83-byte hints, eight-row w1) and the
scalar references in `src/ZKNOX_dilithium87_core.sol`.

* **Lane bound**: seven columns take the raw matvec lanes up to
  119 q^2 + q*2^28, above the q*2^30 offset of the folded first inverse pass
  of ML-DSA-44 / -65. The ML-DSA-87 kernel uses q*2^31 and q*2^32 instead
  (DECISIONS.md ADR-012); `test_matvec_row87_saturated` exercises the four
  worst cases and fails with either of the old offsets.
* **Key**: 67,680 bytes passed in the calldata of every verification, 64
  polynomials of `[32][32 words]` (A row by row, seven per row, then t1), then
  tr. Nothing is stored on chain; `setKey` checks the length and returns the
  key. `js/mldsa87.js` `publicKeyToBlob87` produces it from a 2592-byte FIPS
  204 public key.
* **Signer**: `js/mldsa87.js` / `node js/sign87.js` on `@noble/post-quantum`;
  `make test_signer87` replays the NIST vectors of `test/KAT/`.
* **KATs** (`test/KAT/`, as given by NIST): `PQCsignKAT_Dilithium5.rsp`
  (100 vectors, FIPS 204 ML-DSA-87; count 0 is `test/dilithium87KATS.t.sol`,
  the first 10 counts go through `test/dilithium87_vectors.t.sol`, all 100
  through `make test_kat100_87`) and the ACVP `ML-DSA-87` groups of
  `ML-DSA-{keyGen,sigGen,sigVer}-FIPS204/internalProjection.json`
  (usnistgov/ACVP-Server); the 15 sigVer vectors of the external / pure
  interface are checked on-chain with NIST's expected verdicts.
* **Cost**: 1,633,524 of execution, 934,400 of calldata (858,840 for the
  key), 2,584,979 for the whole transaction on the KAT, 72,640 bytes of
  calldata (`test/dilithium87_key.t.sol`).
* **Tests**: `make test_verifier87`; `make bench` includes `MLDSA87`.
* **Deployment**: `script/deploy_dilithium87.sh` / `DeployDilithium87.s.sol`
  (needs `F1600_HELPER`, the same Keccak-f[1600] helper; checks the NIST KAT
  on the deployed verifier). Runtime size 23,803 bytes.

## EXAMPLE 
An example of key generation, signature and verification in python is provided in the directory `pythonref/`.
It is also possible to verify a signature on-chain on Sepolia Testnet. See [here](pythonref/README.md#example) for more details.
Locally, a signature verification can also be verified in Solidity, as illustrated in [this file](test/ZKNOX_dilithiumKATS.t.sol) with a KAT vector from the NIST submission. Further examples will be available in Kohaku project (Ethereum Foundation).

## CONCLUSION
This repo provides an optimized version of DILITHIUM. Order of magnitudes were gained compared to other implementations. Despite those efforts, it is not feasible to reach the same cost as [Falcon](https://github.com/ZKNoxHQ/ETHFALCON) post-quantum signature. The implementation takes advantage of the NTT implementation of [this repository](https://github.com/ZKNoxHQ/NTT). The main reason for adopting Dilithium for Ethereum is the simplicity and efficiency of the signer algorithm for hardware wallet.
